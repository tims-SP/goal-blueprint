# 独立盲审运行指令

> 运行者请在一个全新、独立的模型会话中使用。不要把本文件以外的项目历史、Issue、答案、研究报告或仓库 README 提供给受测模型。

## 运行前准备

1. 复制 `tests/replay/cases/C01-design-handoff.md` 至 `C06-media-identity.md` 六份输入。
2. 准备两个独立的新会话（或两个上下文完全隔离的模型实例），使用相同模型版本、推理设置和 token 预算。
3. A 会话只使用基线审查提示；B 会话只使用候选门禁提示。不要让任一会话看到另一组输出。
4. 每个案例分别提交，保存未经编辑的完整输出、模型标识、时间、推理设置和耗时。
5. 全部输出锁定后，才允许裁判读取 `answer-key.md`。

## A — 基线提示

请审查本项目的开发前需求和设计是否清楚、完整、合理，并提出必要的改进建议。不要编写代码。请输出 READY / NEEDS_DECISION / NOT_READY、发现的问题、证据位置、风险、最小修复建议，以及不应提前实现的事项。

## B — Goal Spec 候选提示

请在 Goal 自主执行前进行规格审查：核对原始目标与真实用户任务是否闭环；跨模块契约、业务语义和约束是否完整传递；重大架构决策是否有可逆性和成本依据；关键技术假设与环境权限是否有证据；验收条件是否客观、可比较且不易被替代；最终文件是否有明确批准与冻结边界。每项发现必须指出输入证据、失败后果与最小充分补救。不得把开放探索的灵感自动变成正式功能；不得以假想风险为由增加无关模块。

## 交付记录

每个案例记录：
- 原始模型输出（不改写）
- 模型和运行配置
- 运行成本与时间（若可见）
- 裁判逐项评分及理由
- 误报、无端功能扩张、错误冻结、错误阻塞

禁止：
- 受测模型访问 `answer-key.md`、`pilot-report.md`、`retrospective-audit.md`
- 提示中出现 Issue 编号、真实故障结论或答案关键词
- 审查结束后补充“它其实应该发现……”并计为命中
- 将重建或合成案例的结果宣传为历史预测准确率

## 判定

样本只有 6 个，结果用于发现方法缺口，不用于宣称统计显著或普遍优越。若 B 组只增加发现数量，却同时显著增加无依据阻断和架构膨胀，则不能判定候选门禁优于基线。
