# C06 预执行门禁评审 — 媒体实体的身份设计

## 1. 结论：NEEDS_DECISION

**可以启动的前提**：把下述 F1、F2、F6 三处以 3–6 行文字补进 spec（属于"修 spec"，不是"改架构"），即可放行一次**受限的评估型交付**。

**不可直接放行的原因**：spec 内部存在一处硬矛盾（路径主键 ↔ 一个媒体多版本），且"任务"一行同时可被读成"给出评估"或"做出调整"。对一个长时间自主运行的 Goal agent 而言，这两点分别意味着"必须自行做出不可逆的基础性身份决定"和"可以顺手把 schema、迁移、同步就绪字段都写出来"。两者都不会被静默发现，而是被静默执行。

> 证据等级标注 `SYNTHETIC`：本次评审按"5 条功能需求是唯一边界"处理，不把"已确认"当成用户验证过的真实需求（见 F8）。

## 2. 发现（按严重度排序）

### F1 — Blocker：`media_id` = 绝对路径，与"一个媒体关联多个版本"直接冲突
- **原文**：`数据表的主键 media_id 直接等于文件的绝对路径` ＋ `一个媒体关联多个不同版本的视频文件` ＋ `存储位置通过文件路径区分`
- **自主执行失败模式**：在路径主键下，media→N 个文件在关系上不可表达。代理只有两条路：**(a)** 违反 `media_id` 唯一性，用多行拼出多版本 → `其他模块引用 media_id 获取媒体` 的契约随之破裂，播放/清单/用户编辑的引用错位到错误文件；**(b)** 自行推翻路径主键、改用代理键并连带重写全部引用方契约 —— 这是一个昂贵且难以回退的基础性决定，而 spec 恰恰把这个决定留给了一个无人审阅的自主进程。
- **最小修复**：在 spec 中写死基数规则 —— `media_id` = 稳定代理键；路径下沉为 `media_file`（版本）表，每行一个物理文件，携带 path / size / mtime / hash / 来源；**path 是版本的可变属性，不是身份**。

### F2 — Blocker：路径主键下"移动后保留人工元数据"不可满足
- **原文**：`从磁盘移动视频后重新扫描而保留人工元数据` vs `媒体标题、描述、用户编辑字段直接挂在此主键下`
- **自主执行失败模式**：路径即主键 ⇒ 移动即换主键 ⇒ 重扫看到的是"新媒体"，人工标题/描述成为孤儿。代理要维持需求，就必须发明"这两个路径是同一媒体"的判据（文件名 stem？同目录？size+mtime？inode？哈希？）—— 这是凭空发明产品需求；退而求其次做全表路径重写，在移动发生于操作系统层时根本无从获知旧→新映射（应用没有事件、没有索引可依赖）。
- **最小修复**：spec 必须回答两点：(a) 移动是否由应用自身执行（是 ⇒ 路径在同一事务内更新，需求天然满足）；(b) 若为外部移动，规定重关联判据 —— 建议 `路径不参与匹配；size + 时长/码率一致，或内容哈希一致` 方可认定为同一媒体，否则新建条目并将原条目标记为"缺失"而非删除。**若 (b) 仍不确定，则要求交付物把它列为"需用户拍板的开放决策"，禁止代理自行定案。**

### F3 — High：把可变文件系统状态泄漏为跨模块引用键
- **原文**：`其他模块引用 media_id 获取媒体`
- **自主执行失败模式**：重命名/换挂载点使全部下游引用失效或被迫级联更新；PATH 作键还附带：大小写不敏感文件系统上唯一性无法保证、路径长度与 URL 转义问题、跨机器绝对路径不可移植。任一模块若把 `media_id` 当 URL 片段或文件名使用，都会立刻暴露这些缺陷。
- **最小修复**：写明引用契约 —— 下游只引用稳定 `media_id`，路径在读取时经版本表解析。把"代理键"作为最小必要调整的理由陈述即可，**不得顺延到任何同步相关字段**（见 F7）。

### F4 — High："版本"语义与字段归属未定义
- **原文**：需求只写 `一个媒体关联多个不同版本的视频文件`；候选设计只写 `媒体标题、描述、用户编辑字段直接挂在此主键下`
- **自主执行失败模式**：代理必须自行界定"什么算同一媒体的两个版本"以及哪些字段是媒体级、哪些是文件级（清晰度/编码/字节数/时长/校验和/来源），并据此建表 —— 这属于发明需求而非实现细节，且决定了整张表的形状。
- **最小修复**：写明 —— 媒体级：标题、描述、用户编辑字段、媒体与文件的关联；文件级：路径、字节数、时长、分辨率、编码、哈希、来源。"新扫描到的文件如何归入既有媒体"若不规定，则明确**不在本次范围**，并要求在交付物中作为开放问题上报。

### F5 — Medium：多存储源的身份边界仅由路径隐含表达
- **原文**：`扫描多个本地存储源` ＋ `存储位置通过文件路径区分`
- **自主执行失败模式**：同一文件经挂载别名/符号链接被扫两次即产生重复条目；macOS 大小写与 Unicode 规范化差异导致同一文件两条记录或匹配失败；Windows 大小写不敏感 FS 上"主键唯一"形同虚设。
- **最小修复**：要求交付物显式写出路径比较的归一化规则（大小写、Unicode NFC、符号链接解析），并把"是否需要独立 source_id / 卷标识"作为开放问题上报。

### F6 — Medium（自主执行风险最高）：交付物形式与完成判据缺失
- **原文**：`任务：评估此数据模型是否满足当前已确认的需求，以及是否需要更小的基础性设计调整`
- **自主执行失败模式**：agent 无法判定"完成"，也不会产出可验收结论；更糟的是它把任务读成"改造并实现"，直接改 schema、写迁移脚本、搭扫描器、加同步就绪字段 —— 既越权又不可逆。
- **最小修复**：规定交付物 = 一份设计决策说明（落到仓库固定路径），必含五节：① 逐条需求的满足/不满足判定表；② 建议的身份模型 DDL（唯一变更面）；③ 移动 / 重扫语义；④ 被否方案及原因；⑤ 明确的开放问题清单 + 越界声明（本次不改代码、不建库、不实现同步）。完成判据 = 五节齐备、每条需求有明确结论、开放问题已上报。

### F7 — Medium：同步的"不做"边界需要更硬
- **原文**：`未来云同步尚未纳入本次范围；不允许预先实现同步服务`
- **自主执行失败模式**："路径不能做身份"极易被推演为"预留 remote_id / provider 抽象 / 冲突字段"，即预实现同步 —— 恰好违反明确约束。
- **最小修复**：列出禁止项：不得出现 remote_id、platform、provider 接口、冲突合并、后台同步监听器；允许的只有一句理由陈述："代理键对未来扩展更友好"。

### F8 — Medium（证据层）：合成需求不等于用户验证
- **失败模式**：把"已确认功能"当成真实用户需求，进而补齐未列出的功能（版本选择 UI、标签体系、刮削、多用户）。
- **最小修复**：spec 声明 5 条为本次唯一需求边界，禁止以"用户大概需要"为由增加功能；结论需标注其依据为合成需求。

### F9 — Medium（缺失证据）：是否 greenfield 未声明
- **失败模式**：若仓库中已存在以路径为主键的实体库，则"保留人工元数据"从"新设计问题"变成"存量数据迁移与保全问题"，最小调整的代价完全不同。
- **最小修复**：spec 明确当前是全新设计还是对既有实现的改造；若为后者，必须补一条迁移/兼容要求再重开范围。

## 3. 阻塞项 vs. 可由 Goal agent 自行决定的实现细节

**阻塞项（必须在交付前由用户拍板或写进 spec，共 3 项）**
1. **F1 基数规则**：身份与位置是否分离（代理键 + 版本表）。这是不可逆方向。
2. **F2 重关联语义**：移动是否由应用执行；外部移动时"同一媒体"的判据。
3. **F6 交付边界与完成判据**：评估型交付，禁止实现扩张。

**可降级为"必须上报的开放问题"、由 agent 列举但不得自行定案**：F3 引用契约的最终措辞、F4 版本与字段归属、F5 归一化与 source_id、F8 边界声明、F9 greenfield 状态。

**明确属于可逆实现细节，放手让 agent 决定**：SQL 方言与建表语法、UUID v4/v7、内容哈希算法（sha256/blake3）、字段长度与索引、DDL 排版与命名风格、是否使用 ORM、是否附示例查询与注释、前端/后端目录与语言选型、文档排版。

## 4. 门禁必须拒绝的范围扩张与过度设计

- 任何同步物化：同步服务、远端 ID、provider 适配层、冲突合并、后台同步任务
- 完整扫描器/索引服务/文件监听 watcher/任务队列/调度
- 转码、缩略图、播放器、媒体服务器、UPnP/DLNA
- 元数据刮削（TMDB 等外部源）、多用户与权限、标签/收藏体系
- 迁移框架、ORM 脚手架、seed 数据、API 层、容器化与部署脚本
- 借"顺手"改写需求列表（第 6、7 条功能）、补 PRD/用户画像/UI 原型/NFR/性能指标
- 为尚未确认的存量数据或远端同步预建结构

---

## 5. 已经充分、不应再扩张的部分

- **5 条功能需求已足以界定本次身份设计的工作面**：不需要更细的 PRD、用户故事、验收矩阵、度量指标或上线计划。
- **候选设计的意图是合理的出发点**："路径区分存储位置、用户字段挂媒体"无需推翻；所需的基础性调整很小且可逆 —— **把身份与位置拆开：`media` 持稳定键与人工字段，`media_file` 持路径与文件级属性，一行一个版本**。
- **"同步不在范围内"已足够**，不需要再补同步路线图章节；代理键对未来的友好性只需一句理由。
- **"识别视频"的判定标准**（扩展名白名单 vs 探测）属于可逆实现细节，本次不必先定。
- **已有明确排除项时不应新增"通用来源抽象层"**：多个本地存储源是本次唯一的多源场景。
