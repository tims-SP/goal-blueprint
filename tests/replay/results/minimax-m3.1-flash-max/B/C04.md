# 门禁结论

**Verdict: NEEDS_DECISION**

**一句话理由：** 目标本身可执行、方向无矛盾，但材料在**四个权威性/业务语义点上把"产品决策"伪装成了"实现细节"**——尤其"谁是约束权威来源"和"遗漏如何识别"（题目自陈的缺口）、"冲突结果的契约形状"、"版本感知的数据来源"、以及"进入 Suspended 时暂停原因是否必填"。这四项一旦由长跑 Agent 自行拍板，产出在语义上不可验收，且纠偏成本高（对外错误契约与数据模型污染）。补齐 **5 项决策 + 1 项默认口径**（约 20 行文字）即可放行，不需要重写设计。

其余为中等严重度但可由 Agent 依现有代码惯例自行判定的事项，不构成阻塞。

---

## 一、阻塞项（需需求方拍板，材料内无解）

### B1 · 权威来源与"遗漏识别"规则缺失
- **证据**：*"二者都属于设计材料，但没有明确规定何者是约束的权威来源，也未定义如何判断任务描述是否遗漏了字段级约束。"*
- **失败模式**：Agent 面对"SuspendReason 200 上限"（表）与"去首尾空格 + 备注校验"（任务）时无裁决依据。长跑 Agent 的典型行为是**取交集并静默补齐**——它会把"trim"理解成"数据模型之外的新约束"，或把"200"理解为仅适用于 Remark。两种读法都产生**自洽但错误**的验收基线，且 Agent 不会报错。
- **严重度**：高（直接决定所有后续行为是否正确）
- **最小修复**：写 3 条裁决规则 —— ① 字段级约束（类型/可空/长度/默认）以数据模型表为唯一权威；② 行为与流程以任务描述为权威；③ **任务描述不得放宽数据模型的硬约束**（长度、可空性），需要放宽即属任务描述缺陷 → 记录并升级，不得静默实施。配套"遗漏识别"机制：开工前输出**逐字段对照清单**（表中有/任务中有/是否冲突），凡两表未共同覆盖的字段级约束，一律列入待确认清单而非自行发明。

### B2 · "冲突结果"的对象与返回契约未定义
- **证据**：*"进行 200 字符备注校验，并返回明确的冲突结果"*；*"更新版本感知的状态变更逻辑"*
- **失败模式**：句法上"冲突结果"紧跟"备注校验"，语义上却来自"版本感知"——至少三种读法：① 字段校验失败（超长）；② 乐观锁版本不匹配；③ 非法状态迁移（如已挂起再次挂起）。Agent 任选其一，都会产出**互不兼容的错误载荷**（错误码、异常类型、字段名、是否含 expected/actual version、HTTP 状态码全不同）。下游一旦按错误形状编码，返工成本高。
- **严重度**：高（对外契约，昂贵到难以逆转）
- **最小修复**：列出**冲突类别清单**（建议 ≥3 类，各给稳定 code），并规定形状："沿用现有系统既有的冲突返回约定；若无既有约定，统一为 `{code, field?, expectedVersion?, actualVersion?}`，由错误处理中间件序列化。"

### B3 · "版本感知"在数据模型中无对应物
- **证据**：数据模型草表**只有两行新字段，无版本字段**；任务却要求*"更新版本感知的状态变更逻辑"*。
- **失败模式**：两种读法——(a) 既有实体上已有的 revision/乐观锁列；(b) API/Schema 版本号。Agent 若撞上不存在的版本概念，会**自造一个 version 字段并改造更新路径**（数据模型污染 + 并发语义错误）；若撞上 schema version，则整个"版本感知"是词不达意。
- **严重度**：高
- **最小修复**：一句话指认版本真源（"沿用实体既有的 `<列名>` 版本列，保护 `<读/写/状态变更>` 操作"），或确认现有系统无此机制并删除该措辞。

### B4 · 状态相关的条件必填未定义（业务语义）
- **证据**：*"SuspendReason | 可选字符串，最长 200 字符"* vs 字段名与任务中的*"暂停原因"*、*"状态变更逻辑"*。
- **失败模式**：**"可选"是存储级可空**，业务上"迁移到 Suspended 是否必须携带暂停原因"完全未知。Agent 选"不阻断"→ 缺业务规则；选"阻断"→ 破坏既有合法调用方（历史上无理由挂起的数据无法再挂起）。两种结果都无法向需求方验收。
- **严重度**：高（唯一一处真正的业务政策）
- **最小修复**：明确二选一：① 迁移到 Suspended 时 SuspendReason 非空，否则返回冲突码 `SUSPEND_REASON_REQUIRED`；② 无条件必填约束，仅存不校验。附带说明存量调用方是否受影响。

### B5 · 目标上下文缺失（实体/入口/持久层）
- **证据**：*"一个已有管理系统需要增加两个可选字段"*——未点名实体、模块、读写入口、迁移要求。
- **失败模式**：Agent 在陌生代码库中面对"状态变更逻辑"这一模糊指针，**默认路径是新建实体/新表/新服务**——正是范围膨胀的典型触发器；也可能是改错模块。
- **严重度**：中高
- **最小修复**：点名实体与受影响入口（"仅在既有 `<实体>` 的创建/更新/状态变更路径中接入两字段，不新增表/服务"），并说明是否需要存量迁移（预期答案：因字段可选，**不需**回填）。

## 二、可在实施中判定，不阻塞（但需写入口径，否则易翻转）

| # | 事项 | 证据/缺口 | 失败模式 | 严重度 | 最小修复 |
|---|---|---|---|---|---|
| D1 | **Trim 的适用范围与顺序** | 任务只提"去除首尾空格的暂停原因"，未提 Remark | Remark 是否被 trim 未定：若被 trim，**用户原文被静默改写**（数据损失）；SuspendReason 先 trim 还是先计数未定（205 字符带空格 → trim 后 195 通过，或先计数失败） | 中高 | 明写："仅 SuspendReason trim；trim 先于长度计数；**落库值为 trim 后值**"（或反向，逐条选定） |
| D2 | **"200 字符"计数口径与边界** | 表只写"最长 200 字符" | 码点 / UTF-16 单元 / 字节三种口径；含 CJK 与 emoji 时结论不同；`≤200` 还是 `<200` | 中高 | 明写："按 Unicode 码点计数，200 为含端点" |
| D3 | **SuspendReason 是否在运行时做长度校验** | 表约束两字段 ≤200，任务只点名"备注校验" | 严格照任务字面 → SuspendReason 超长穿透至持久层报错或被截断 | 中高 | 明写："两字段均在输入层执行 ≤200 校验" |
| D4 | **可空/空串/全空白语义** | "可选"未定义默认值形态 | 响应与落库出现 null vs "" 分叉；下游相等判断破裂 | 低中 | 默认"全空白→null；沿用代码库既有可选字段惯例" |
| D5 | **版本冲突的写入原子性** | 未提及 | 版本不匹配时是否部分写入 | 中 | 默认："冲突时不发生任何写入" |
| D6 | **"版本感知"的作用范围** | 未指明哪些操作受版本保护 | 读操作也被加锁等过度实现 | 中 | 默认："仅状态变更写操作" |

**注：** D1–D3 若不给口径，建议**明确写入 Goal 任务书**而非留给 Agent 推断——它们直接决定"接受/拒绝"这一可观察行为，属于口径而非口味。

## 三、门禁必须拒绝的范围膨胀与过度设计

| 膨胀项 | 为什么必须拒 |
|---|---|
| 新建实体/表/服务/存储层以"放"两个字段 | 需求只说"增加两个可选字段"；且触发 B5 |
| 搭建通用校验框架 / 重构既有校验器 / 引入新校验库 | 需求只要"备注 200 校验 + 去空格"，框架化属自主扩大 |
| 对系统内**其他**字符串字段统一 trim | 需求只指定暂停原因；全局 trim 会改写他处数据 |
| 新建错误码体系 / 错误文案国际化 / API 版本化 | B2 只要求"明确的冲突结果"，不要求体系 |
| 审计日志、变更历史、软删除、状态快照 | 未在范围描述中出现 |
| 追加未声明约束：最小长度、正则、非空、字符集、唯一性、DB CHECK | 草表只声明可选 + ≤200；自行加约束=发明需求 |
| 回填历史数据 / 把可选字段改为必填 / 加非空迁移 | 与"可选"直接冲突 |
| 大范围重构"版本感知的状态变更逻辑" | 应限于让这两个字段正确接入 |
| 自行产出对外 API 文档站 / OpenAPI 全量重写 / 前端契约 | 不在交付物描述内 |

## 四、已充分，不应再扩写

以下内容在材料中已闭合，**Agent 不得再讨论、不得再"优化"**：

- 两个字段的**名称、字符串类型、可选性、200 字符上限**——不必再论证是否加索引、是否加 DB 约束、是否需要统一封装结构体。
- **四项行为项**（版本感知的状态变更更新、暂停原因去首尾空格、备注 200 校验、返回明确冲突结果）——已列举，**不得自行追加第五项校验规则**（正则、格式、脱敏、敏感词等）。
- **"可选"语义**：已定 → 不需回填、不需默认值迁移、不破坏既有调用方。
- **需求规模**：这是一次两字段增量，**不需要 PRD、用户故事、原型、里程碑文档**；门禁不授权把设计材料扩写成产品文档。

## 五、最小决策清单（可直接"按建议默认批准"）

| # | 决策项 | 建议默认 | 若与默认不同会怎样 |
|---|---|---|---|
| 1 | 权威与升级规则 | 见 B1 三条裁决 + 逐字段对照清单 | 基线翻转，验收全错 |
| 2 | 冲突类别与形状 | 3 类（超长 / 版本不匹配 / 非法迁移）+ 统一载荷 | 契约不兼容，返工 |
| 3 | 版本真源 | 既有实体的版本列，仅保护状态变更写操作 | 误造版本字段 / 语义错位 |
| 4 | SuspendReason 条件必填 | 迁移到 Suspended 时必填，冲突码 `SUSPEND_REASON_REQUIRED` | 业务规则缺失或存量流程被打断 |
| 5 | Trim 口径 | 仅 SuspendReason；trim→计数→校验；落库为 trim 后值 | 接受/拒绝结论分叉 |
| 6 | 计数口径 | Unicode 码点，≤200 含端点 | CJK/emoji 边界用例不一致 |
| 7 | 运行时校验覆盖面 | 两字段均校验 | SuspendReason 超长穿透持久层 |
| 8 | 目标实体与入口 | 既有实体既有读写/状态变更路径，不新建表；无需回填 | 新建实体，范围失控 |
| 9 | 可空默认 | 全空白归一为 null；沿用代码库惯例 | API/DB 形态分叉 |

## 六、建议写入验收判据的可执行用例（供 Goal agent 自检，非新增需求）

1. `SuspendReason = "  停电检修  "` → 落库 `"停电检修"`（trim 后），长度按 trim 后计数。
2. `SuspendReason` trim 后 201 字符 → 返回冲突，载荷含字段名与实际长度，**不发生写入**。
3. `Remark` 201 字符 → 返回冲突（Remark 不 trim，含首尾空格计入长度）。
4. `Remark = " 备注  "` → 原样保留（不 trim），或按第 5 项决策的统一口径。
5. 版本号不匹配 → 返回版本冲突，含 expected/actual version，**无任何写入**。
6. 迁移到 Suspended 且 `SuspendReason` 为空 → 按第 4 项决策返回指定冲突码。
7. 合法迁移 → 成功，两字段按上述口径写入，既有调用方（不传新字段）行为不变。

---

**放行条件**：第 1–8 项决策（或"按建议默认批准"）写入交接材料 + 明确"冲突结果沿用既有约定、无既有约定时用统一载荷"后，可放行执行；并建议把"输出逐字段对照清单（表/任务/冲突/待确认）"设为 Goal agent 的**第一个里程碑**，作为遗漏识别机制落地证据。

**一句话提醒**：本门禁**不授权**任何实现，也不授权把两份设计材料扩写成产品文档；它只要求在开工前把"谁是权威"与"冲突结果长什么样"这两个问题交还给需求方。
