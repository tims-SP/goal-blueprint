# 门禁结论：READY（可开工，无需新增架构功能或重大产品决策）

**回答规格自带的那个问题：不需要。** 该简明规格已包含全部阻塞级决策——目标、输入、输出、不变量、负向边界、错误行为、验收场景五要素齐备，无矛盾、无缺失外部证据、无数千行级别的不可逆架构决策。规格中**根本不存在**需要补齐的架构面（单进程、单文件、无状态、无持久化、无第三方依赖）。

唯一需要补的是一组**开工第一步就要钉死的口径**（退出码取值、输出列集、CSV 方言、表头匹配规则）。这些不是"用户决策"，而是"不钉死则验收脚本无法写出唯一期望"的实现细节——它们成本极低、完全可逆，**不构成阻断**。

## Findings（证据 → 失败模式 → 严重度 → 最小修复）

**F1 退出码取值未定义｜中**
证据：`缺列则不创建输出文件并返回错误`、`输出路径已存在时拒绝覆盖`、`验证每种结果、退出码及原文件保持不变`。
失败模式：验收要求"验证退出码"，但规格未给码值；agent 自选后，任务完成判定失去唯一真值，且不同实现批次互不兼容。
最小修复：`0`=成功；`1`=用法错误/缺列；`2`=输出已存在（拆分或合并均可，但必须写进测试期望表）；错误信息写 stderr。

**F2 输出列集与表头行未写死｜中**
证据：目标仅称`读取 UTF-8 CSV 的 name、email 两列，输出到新 CSV`。
失败模式：输入含多余列时，"只输出两列"与"透传全部列"两种实现都能字面满足规格，却产出不同文件；验收无法判定对错。
最小修复：写死"输出保留原表头行与全部列，仅对 `name`/`email` 两列做变换"（或明确只输出两列），并在验收中加入一条多列输入断言。

**F3 CSV 方言与行尾未定义｜中**
证据：全文仅出现`UTF-8 CSV`，无分隔符、引用、行尾约定。
失败模式：Python `csv.writer` 默认 `lineterminator='\r\n'`，LF 输入会产出 CRLF 输出 → 字节级比对失败；分隔符/引用处理差异直接导致字段切错位。
最小修复：读入按逗号分隔 + RFC4180 双引号引用；输出行尾固定 `\n`（或与输入一致），在验收期望中显式标注。

**F4 表头匹配规则未定义｜低-中**
证据：`缺列则…返回错误`（隐含按表头名查找），以及 BOM 条目`按 UTF-8 处理`。
失败模式：`Name,Email`、` name ,email` 被误判缺列；带 BOM 文件首格残留 `\ufeffname` 未剥离，导致 BOM 用例反而报"缺列"——与 BOM 条目自相矛盾。
最小修复：表头名去首尾空白 + 大小写不敏感匹配；解码用 `utf-8-sig`（等价于先剥 BOM 再按 UTF-8 读）。

**F5 空白与大小写的语义边界｜低**
证据：`去掉每个字段首尾空格`、`将 email 规范为小写`。
失败模式："空格"可能仅指 U+0020，而真实脏数据含 `\t`、NBSP、U+3000 全角空格；另存在 agent 误把 `name` 一并小写的风险。
最小修复：trim 覆盖 Unicode 空白集合；**仅** email 做 ASCII 小写；`name` 保持大小写不变（规格已隐含此点，需写进实现说明以防误扩展）。

**F6 "先 trim 还是先判空"顺序不明｜低**
证据：`空 email 原样保留为空` 与 `去掉每个字段首尾空格` 在全空白 email（`"   "`）上语义相冲。
最小修复：规定顺序为 trim → 判空 → 保留为空（输出空字段）。

**F7 错误优先级未定义｜低**
证据：两条错误规则并列出现，无先后。
失败模式："缺列"与"输出已存在"同时成立时报哪个不确定，stderr 文案与退出码不稳定。
最小修复：缺列优先校验；两条规则共同点（不创建输出文件、非零退出）已在规格中，agent 只需固化次序。

**F8 输入边界场景未覆盖｜低**
证据：验收仅列`正常、缺列、空 email、已有输出文件、带 BOM`五例。
失败模式：空文件、仅表头文件、非 UTF-8 编码文件行为未定义，可能表现为未捕获异常 traceback（退出码不稳定）而非干净报错。
最小修复：空文件按"缺列"报错；仅表头 → 输出仅表头；解码失败按"输入非法"报错（同样不创建输出文件、非零退出）。

**F9 CLI 接口面未定｜低**
证据：全文未出现任何参数形式。
失败模式：`--output` / `-o` / 位置参数三种形态互不兼容，验收脚本需跟着改。
最小修复：固定"输入为位置参数、输出用 `--output/-o`"（缺省值可选 `*.cleaned.csv`）。属纯可逆接口，无需用户决策。

**F10 "原文件保持不变"缺可比对机制｜低**
证据：`验证…原文件保持不变`。
失败模式：仅凭肉眼无法判定无改动；实际还需覆盖 mtime/权限。
最小修复：测试中断言 SHA-256 与 mtime 均未变。

**F11 冻结与变更审批缺一句明文｜低（流程项）**
证据：规格无"规格冻结后谁可批准范围变更"的表述。
失败模式：agent 在实现中"顺手"加需求（最常见的就是邮箱格式校验）且无人拦截。
最小修复：在冻结版本补一句"任何超出上述范围的行为改动须用户重新批准"。

## 阻断项 vs 可由 Goal agent 自行决定的实现细节

**阻断项：无。** 不存在必须先由用户拍板、否则开工即走偏的事项。

**开工第一步须钉死（否则"完成"不可判定，但属 agent 决策）**：F1 退出码表、F2 输出列集、F3 CSV 方言与行尾、F4 表头匹配规则。这四条写进实现说明与验收期望表即可，建议占用一页。

**agent 可全权决定**：语言与运行时（Python 标准库 `csv` 即可，无需 pandas/requests 等依赖）、CLI 库、文件组织、输出用临时文件 + rename 原子落盘、fixture 具体数据、测试框架与断言形式、错误文案与日志形式、trim/lower 细节（F5/F6）、边界行为（F7/F8）、CLI 形态（F9）、校验和方式（F10）。这些全部可逆，不产生昂贵返工。

## 门禁必须驳回的范围扩张与过度设计

一旦出现即判不合规，应驳回：

- **邮箱合法性校验、域名语法校验、可达性/SMTP 验证**（规格要求"无联网"，未要求校验；这是最典型的自发新增）。
- **去重、多列支持、通用清洗规则 DSL、插件/规则引擎架构**。
- **stdin/stdout 管道模式**（`只支持本地文件` 已排除）。
- **就地编辑 / in-place 模式**（与`输入文件保持不变`直接冲突）。
- **编码嗅探（chardet 类）、多编码猜测、locale 相关行为**（规格已钉死 UTF-8）。
- **配置文件、日志框架、遥测、CLI 框架（click/typer）、彩色输出、进度条、TUI**。
- **watch/定时/守护进程、多文件与通配符批量、GUI、账号与协作**（规格负向清单已逐条排除）。
- **Docker、CI 流水线、发布到 PyPI/Homebrew、数据库与队列**。
- **"为了架构完整"而分层（ingest/transform/sink + 接口抽象 + 测试金字塔）**——单文件 + 5 个用例足够。

## 已经充分、不应再扩大的部分

- **目标与不变量已闭合**：输入、动作、输出、`输入保持不变` 四要素齐备，无需再写 PRD 级文档或 ADR 集合。
- **负向边界已存在**：无需 agent 再补写"非目标"章节。
- **架构面为零**：无需分层、包结构、依赖注入、配置抽象。
- **验收方式已定**：5 个样例脚本化断言即可，不需要覆盖率目标、性能基准、属性测试/模糊测试。
- **输入不可变已被结构性保证**：`输出路径已存在时拒绝覆盖` + 输出必须是新文件 ⇒ 写回输入路径在规则上不可能，F10 的校验只是佐证而非新需求。
- **不需要多版本兼容、i18n、审计、幂等/重放机制**。

**建议的下一步（不新增范围）**：先写一页"口径钉死表"（退出码表、输出列集与表头规则、CSV 方言与行尾、trim/大小写/判空顺序），再落 5 份固定 fixture 与期望字节，随后即可进入实现与自测。
