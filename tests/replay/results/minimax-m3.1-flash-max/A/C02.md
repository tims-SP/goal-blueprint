# C02 搜索需求 — 标准设计评审## 1. 结论（Verdict）

**NEEDS_DECISION** — 需求意图清晰，但**按现状不可交付实现**。FR-SEARCH 只有一句话断言结果，不断言可观察的匹配规则、结果契约与失败行为；方案段引入的"通用搜索组件 + 统一候选"又引入了一组未定义术语和未闭合的接口边界。缺口集中在 5～6 个**必须由产品方拍板**的语义问题上；在这些决策落地前，编码只能停在脚手架层面。

以下所有判断仅基于所提供的规格文本（含 `evidence_level: RECONSTRUCTED`），未查阅任何外部文件，未引入隐含需求。

## 2. 发现清单

### Blocker

**B1｜"匹配结果"未定义，需求的核心用户可见行为不可判定**
- 证据：FR-SEARCH 原文"用户输入关键词后，搜索返回**所有价格来源的匹配结果**"；全文无任何匹配规则、无查询字段定义。
- 为什么要紧：同一句 FR 可以被实现为"零件号归一化精确匹配"、"品牌+描述全文匹配"、"模糊召回"，三者返回集合差异极大（`M8-40` vs `M840`、前导零、`1234-567` vs `1234 567`、原厂件 vs 售后等效件）。两个实现都可以宣称"满足 FR"，而用户拿到的结果完全不同——这是本需求唯一不可逆的正确性问题。
- 最小修正：用1～2 句改写 FR，使其可判定，例如明确"查询输入为单一关键词文本框；匹配主规则为归一化后的零件号精确匹配（忽略大小写、空格与连字符差异）"，并显式声明本范围内**不做**模糊召回与等效件扩展。

**B2｜"所有价格来源"的失败/超时行为未定义**
- 证据："搜索返回**所有**价格来源的匹配结果"；方案段"一个通用搜索组件对接**所有**数据源"，但全文无失败语义、无来源清单、无"部分可用"表述。
- 为什么要紧：按字面，"所有"意味着全有或全无。单一来源超时 → 整次搜索失败（可用性事故）；而静默返回部分结果在字面上又违反 FR。这是典型的"实现即违背"陷阱：没有决策，两种实现都站得住。
- 最小修正：补一条降级策略，例如"按来源隔离失败；超时/不可用的来源被跳过，结果区显示'部分来源暂不可用'提示；'所有来源'指来源清单内的全部在线来源，而非强一致快照"。同时给出纳入范围的来源清单。

**B3｜结果集合的去重、排序与上限未定义（"统一返回匹配候选"不是契约）**
- 证据："统一返回匹配候选"——仅说明"统一返回"，未说明统一的**结构**。
- 为什么要紧：下游"供应商价格比较能力"以搜索结果为输入。若一个零件来自 5 家供应商，是 1 行（零件 + 报价列表）还是 5 行（报价行）？排序按价格、按供应商优先级、还是按相关度？是否有条数上限？这些直接决定比较页能否成立，也决定搜索页用户看到什么。
- 最小修正：确定结果行的语义单位（建议明确"零件 × 供应商报价"或"去重零件 + 报价集合"二选一）、一个主排序键与并列时的次级键、以及分页/上限策略。

### Major

**M1｜"价格"这一结果字段的业务语义缺失**
- 证据：产品定位"面向零部件报价"、"支持从多个供应商价格来源获取结果"；但全文未定义币种、计价单位（件 / 盒 / 米）、最小起订量、价格有效期。
- 为什么要紧：搜索结果会直接呈现价格。语义缺失时，10.00 与 10.00（USD/件 与 CNY/箱）被并列在同一个列表里，是面向用户的价格误导，且会让后续"价格比较"能力建立在不可比的数字上。
- 最小修正：列出结果行必须携带的最小字段集；或明确声明"FR-SEARCH 仅透传源端原始值，不承诺可比性，价格比较在另一需求中定义"。

**M2｜术语不一致且未定义："价格来源" / "数据源"**
- 证据：FR 用"价格来源"，方案用"数据源"。
- 为什么要紧："来源"是供应商？价格表？API 端点？平台自营目录是否算？用户的协议价/报价单是否算？范围边界不清会直接导致实现时的反复澄清。
- 最小修正：给"价格来源"一个唯一定义 + 一份本次纳入范围的来源清单，后续全文统一使用该词。

**M3｜缺少可测的验收标准与空结果/异常输入的用户行为**
- 证据：全文唯一的验收性表述是"返回所有价格来源的匹配结果"。
- 为什么要紧：无验收标准 = 无"完成"定义；空结果、部分有结果、单条结果、超长/空白/特殊字符查询是否允许、搜索是提交触发还是输入即搜，均无定义，用户可见行为存在空白。
- 最小修正：补 4～6 条 Given/When/Then，至少覆盖：正常命中、无命中、空查询、单一来源失败、结果排序。

**M4｜与零件选择 / 价格比较的边界未闭合（规格自己已承认）**
- 证据："产品也包含零件选择和供应商价格比较能力，但**尚未提供这些能力在页面中的用户任务流程描述**"。
- 为什么要紧：搜索的产物恰好是这两项能力的输入接口。零件选择由谁拥有（搜索结果页内选择，还是跳转到零件页）未定义，会造成后续实现返工或两处各自实现。
- 最小修正：一句话写明 FR-SEARCH 的输出类型（零件 ID / 报价条目 ID / 两者）与交接点，并注明零件选择与比较流程由独立需求跟踪，不在本次范围内。

**M5｜"通用组件对接所有数据源"的架构契约缺失**
- 证据："一个通用搜索组件对接所有数据源"。
- 为什么要紧：这是典型的异构扇入设计。没有规范化边界（统一结果模型 + 每源适配器职责：映射、归一化、超时、错误分类）与源能力差异说明（有的源无品牌、无 MOQ、无币种），"通用组件"会退化为特例堆叠。
- 最小修正：给出统一结果模型与适配器职责契约；并把并发/超时/缓存等留作实现细节（见第 5 节）。

**M6｜结果的账号/租户作用域未定义**
- 证据：全文无授权、租户、区域相关表述。
- 为什么要紧：B2B 报价场景中，协议价/区域可售性通常按账号区分。若所有登录用户看到同一份价目表，可能呈现该客户无权成交的价格——用户可见且有商业后果。
- 最小修正：一句作用域声明（例如"所有登录用户可见同一份公开目录价；协议价与区域定价不在本 FR 范围"）。

### Minor

**m1｜规格来源为重建件**
- 证据："evidence_level: RECONSTRUCTED"。
- 为什么要紧：重建件中的隐含假设未标注来源，实现者无法区分"已确认"与"推断"。
- 最小修正：链接原始 PRD/访谈记录，或输出一份假设登记表，逐条标注推断依据。

**m2｜输入范围未闭合**
- 证据："用户输入关键词"，全文未提及是否存在筛选/排序控件。
- 为什么要紧：不是要求补功能，而是要求**显式关闭**——避免实现阶段"顺手加上供应商筛选、库存筛选"。
- 最小修正：注明"FR-SEARCH 范围仅含单一关键词输入与结果列表，不含过滤、排序控件、保存的搜索"。

## 3. 已经充分的部分 / 应保持在外

**已充分（无需再讨论）：**
- 问题域与产品定位清晰：多供应商价格来源 + 零部件报价，搜索作为入口是被合理选中的能力切分。
- 方案方向与 FR 目标自洽："单入口 + 多源扇入 + 统一结果"是合理的架构形态，方向上不需要推翻。
- 规模合适：单功能、单页面区域，可独立交付与验收。
- 规格自身对已知未知的披露是诚实的（明确写出零件选择/价格比较缺少流程描述），且"禁止默认增加新功能"的边界声明有效，应被严格遵守。

**应明确排除在本需求之外（不要顺手加）：**
- 零件选择流程与供应商价格比较流程的页面与交互设计（按 M4 由独立需求承接）
- 过滤器、排序控件、保存的搜索、搜索历史
- 模糊/语义/向量检索、配件等效件扩展、跨语言描述匹配
- 供应商接入方式、爬虫与采集、定价与结算模型、运营后台
- 缓存、分片、限流等具体性能方案（在 B2 决策明确语义后再定）

## 4. 必须由产品/用户决策 vs 可逆的实现细节

**必须由产品方/用户拍板（不可由工程代答）：**

1. 匹配规则与查询字段定义（是否以零件号精确匹配为准、归一化范围、是否含描述/品牌匹配）— B1
2. 单一来源失败/超时时的用户可见行为：降级返回并提示，还是整次失败；"所有来源"的确切含义 — B2
3. 结果行语义：零件为中心还是报价为中心，以及去重与排序键、上限 — B3
4. 价格字段的最小契约（币种、单位、MOQ、有效期）与本 FR 是否承诺可比性 — M1
5. 结果作用域：是否按账号/协议价/区域差异化 — M6
6. 搜索与零件选择的交接点及各自归属 — M4

**属于可逆实现细节（工程可自行决定，评审无需阻塞）：**
- 搜索触发方式（提交 / 输入即搜）、防抖策略、结果区布局与控件形态
- 超时秒数、并发度、缓存 TTL 的具体取值（在 B2 语义确定后自选）
- 适配器技术选型、组件内部结构、库与协议实现
- 分页 vs 滚动加载的呈现形式（在 B3 上限确定后自选）
- 日志/埋点命名、错误码命名、代码组织方式

## 5. 交接建议

1. 先由产品方在第 4 节前 6 项上给出明确答复（预计是1 页决策纪要）。
2. 依据答复改写 FR-SEARCH，使表述可判定（当前句式"所有…匹配结果"建议替换为带范围限定与降级语义的形式）。
3. 补 4～6 条 Given/When/Then 验收标准，覆盖正常命中、无命中、空查询、单源失败、排序。
4. 明确标注本范围不含：过滤器/排序控件、模糊与等效件检索、零件选择与价格比较流程。
5. 在 1～3 完成前，仅可进行不依赖上述语义的技术预研（组件骨架、适配器接口占位），不建议进入业务逻辑实现。

**评审未覆盖且不应在本次范围内追究的部分**：性能指标的具体数值目标、成本模型、供应商接入实现、以及零件选择与价格比较的流程设计。
