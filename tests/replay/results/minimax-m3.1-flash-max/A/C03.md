# C03 规格设计评审（标准评审）

## 1. 结论

**Verdict: NOT_READY**

理由一句话:该文本是**任务章程（charter）**，不是可交付实现的规格。它能支撑"派一个人去做一轮探索性诊断"，但**不能支撑可评价的完成判定**——因为成功与失败都无法在没有基线、目标值和度量口径的情况下被判定，且存在一条"靠少干活把内存降下来"的平凡解路径不被排除。

可行的最小路径不是继续补文档，而是**拆成两阶段**:阶段 0 只做"测量 + 诊断",产出基线与证据;阶段 1 在基线确定后再写入定量目标并实施。

---

## 2. 发现（按严重度排序）

### Blocker

**B1 — 无基线，任何改进率都不可判定**
> "没有附带已确认的基线采样、工作负载、测量环境或定量目标"

为什么重要:内存优化是相对命题。没有基线,"降了多少"没有任何参照,评审只能读到自述数字;不同机器、并发、时间点的 RSS 不可比,变更前后数字的差值可能完全是噪声。
最小修正:规定变更前必须产出基线交付物(同一工作负载、固定重复次数、记录 p50/p95 峰值与稳态值),并把"基线产物本身"列为验收物之一;若环境不可复现,则要求先建立可复现的测量夹具。

**B2 — "明显有效"无阈值,验收条件不可判定**
> "希望优化'明显有效'"

为什么重要:"明显"是修辞不是判据。2% 的下降与 60% 的下降都能被声称"明显有效",自动化 Goal 无法据此终止或回滚。
最小修正:验收改为二选一的量化形式——(a) 相对基线的峰值内存下降 ≥ X%,且 ≥ 测量噪声底 k 倍;(b) 峰值内存绝对值 ≤ 上限 L。X/L 必须由需求方给出(见第 4 节,属真实产品决策)。

**B3 — 缺少"工作量不变量",平凡解未被排除**
> "降低浏览器采集过程的内存使用量……保持功能不退化"

为什么重要:降内存有大量零成本手段:降并发、缩短会话存活、缩减缓存 TTL、跳过重试、提前丢弃页面。内存确实降了,但吞吐与采集完整性同时下降,而"功能不退化"字面上并未覆盖性能与产出量。这是最容易被自动化执行者无意踩中的路径,也是评审最容易漏掉的风险。
最小修正:显式写入不变量——单次运行的采集完成条目数 / 目标 URL 覆盖率不得低于基线的 (1−ε);并发度与吞吐不得以"降内存"为由下调;延迟上界需声明。超出该不变量的优化必须视为功能变更并需单独批准。

**B4 — 工作负载未定义,结论无法归因**
> "浏览器采集服务" / "浏览器采集过程"

为什么重要:"短时突发高水位"与"长驻进程的缓慢泄漏"是两种完全不同的故障,优化对象、验证周期、指标都不同(前者看峰值,后者看时间斜率)。不指定工作负载,就无法判断"修好了"还是"只在一个场景下看起来好些"。
最小修正:指定至少一个代表性工作负载(目标站点集合/页面类型、并发会话数、单次运行时长、会话生命周期),并声明结论仅对该负载成立。

### Major

**M1 — "内存使用"缺口径与采集方式**
> "内存使用'偏高'"

为什么重要:RSS / cgroup 限额 /堆内存 / page cache 差异巨大;峰值与稳态对不同病根(如 OOM kill vs. 成本)的意义完全不同。未定义口径时,可能出现"数字确实下降了,但 OOM 仍发生"。
最小修正:指定主指标与采集点(如 cgroup `memory.peak`,1s 采样 RSS),并指定一个辅助指标;明确验收看峰值还是稳态。

**M2 — 测量环境与噪声底未定义**
> "没有附带……测量环境"

为什么重要:本地/CI容器/生产机的基线不可互换;无噪声底就无法区分"优化生效"与"这次跑得不一样"。
最小修正:固定验收测量环境(含浏览器版本、CPU/内存限额、并发上限),并要求报告中给出该环境的重复采样离散度作为噪声底。

**M3 — 无回归与"端到端验证"的执行定义**
> "并完成端到端验证" / "保持功能不退化"

为什么重要:没有指定必须通过的测试集合与证据格式,验证可以退化为"跑了一下没报错"。另外若现存系统并无 E2E 套件,补建套件本身是显著的范围扩张,需显式授权而非默许。
最小修正:指明必须通过的既有测试/E2E 流程;若无,则把"先建立可复现的 E2E 套件"提升为前置阶段与单独交付物;要求验收报告含前后对照表、方法与原始数据。

**M4 — "允许修改部署配置"的范围边界与回滚缺失**
> "允许修改采集器、资源管理、缓存和部署配置"

为什么重要:部署配置常隐含副本数、超时、限额、调度等语义;修改即可能改变系统行为或影响共享环境,且无回滚要求时风险不可逆。
最小修正:限定在非生产/预发配置;禁止未经批准改动并发度、超时、限额、扩缩容语义;要求附带回滚步骤与生效方式。

**M5 — 前提未经证实,且缺少诊断闸门**
> "`evidence_level: RECONSTRUCTED`" / "内存使用'偏高'"

为什么重要:RECONSTRUCTED 意味着需求本身是重建出来的,"偏高"可能由并发配置、单页载荷、外部服务背压、限额设置错误等多种原因引起;病根不对症时,优化会降低内存却不动真正的瓶颈,甚至引入新的退化。
最小修正:把"证据化诊断"设为强制前置阶段,交付物含 RSS-时间曲线 + 堆/分配快照 + 归因结论;后续每项变更须由该证据支撑,并禁止在归因未完成前改代码。

**M6 — 长期自主执行缺少停止条件与变更预算**
> "拟交给长时间自主执行 Goal 的目标"

为什么重要:没有迭代上限与收敛规则时,自主执行者可能持续微调、扩大重构面,收益递减却风险累积,最终提交一个难以评审的大 diff。
最小修正:设定最大迭代次数/时间预算、"单次变更集规模上限"与停止判据(增益 < X% 或回归风险上升即停并汇报),并要求过程性汇报节点。

### Minor

**m1 — 未列出明确禁止项**:应写明不做浏览器/运行时大版本升级、不新增采集目标、不改协议与输出 schema、不删功能、不做与内存无关的重构与清理。当前"允许修改 X"是白名单,但缺少禁行区,自主执行者可能顺手扩面。

**m2 — 采集输出一致性未约束**:产出数据的保真度要求(逐条等价 / 容许差异)未定义,缓存与序列化改动可能影响输出,应加一条输出等价性判据。

**m3 — 观测与持久化要求缺失**:未要求暴露内存指标、未说明修复是否需在部署后持续观测;若生产曾 OOM-kill,应说明验收针对峰值而非均值。

**m4 — 数据与凭据边界**:诊断用的页面快照、内存转储、浏览器会话/cookie 可能含 PII 与凭据;采集与调试产物的留存、脱敏与访问范围未说明。

## 3. 已经充分的部分 / 应当留在范围之外

**已充分,无需返工:**
- 优化方向明确(降低采集过程内存),目标陈述本身可被非实现者理解;
- 修改许可面(采集器、资源管理、缓存、部署配置)已粗略划定,不是完全开放式的"随便改";
- "功能不退化"这一意图被明确写入,方向正确,只是需按 B3 量化;
- `evidence_level: RECONSTRUCTED` 的诚实标注本身就是质量信号,应保留并据此设置诊断闸门;
- "不要实施任何优化"的本次任务边界清晰,无越权。

**应明确留在范围之外(不要求、评审也不应索取):**
- 本次不实施任何优化、不产出补丁(已明示);
- 不预设优化手段(连接池/复用、缓存淘汰策略、惰性求值、序列化改造、并发模型重写等)——病因未确诊前指定手段属于越权指导;
- 不要求框架/语言/浏览器大版本升级、不要求新采集目标、不要求功能增强或 UI/CLI 改造;
- 不要求与内存无关的重构、依赖清理、测试补全等"顺手"工作(除 M3 明确要求的前置 E2E 套件);
- 不要求多目标(多站点、多负载)全面覆盖,单个代表性负载即可(结论需注明适用范围)。

## 4. 需要真实用户/产品决策的事项(与可逆实现细节的区分)

**属真实决策,必须由需求方拍板(自动化执行者无权自选):**
1. **目标阈值**:相对下降 X% 还是绝对上限 L;以及"可接受的噪声底倍数";
2. **代表性工作负载是什么**(目标站点/页面类型/并发/运行时长)——它决定了优化方向与结论适用范围;
3. **可接受的代价边界**:为降内存可接受多少延迟/吞吐下降、是否允许降低并发(若不允许,B3 不变量即为硬约束);
4. **验收看峰值还是稳态**,以及是否以"不再发生 OOM"为成功定义;
5. **部署配置是否在本轮真实生效范围**,是否允许进入生产,谁批准;
6. **诊断与测试补建的授权**:是否允许在已有 E2E 缺失时新建套件(属范围扩张,需显式批准);
7. **优先级取舍**:若降内存与功能/数据保真冲突,以及不可兼得时的取舍顺序。

**属可逆的实现细节,执行者可自行决定,评审不应设为阻塞项:**
- 具体指标采集实现方式、采样频率、探针选型;
- 诊断工具链选择(profile/pprof/容器指标的具体用法);
- 内部代码组织、配置字段命名、日志与报告格式;
- 是否引入内部缓存封装、是否分批提交、是否开分支;
- 基线重复次数、实验轮次等工程参数(只需满足统计充分性)。

**结论:在第 4 节前 7 项被回答之前,本文档无法升级为 READY。** 其余条目(B1/B3/B4 的指标化、M1–M6)属可由文档与执行者直接补齐的规格完善项,一旦1–7 落定,即可在一次修订内达到可评审状态。
