## 3. 核心判定

### 已验证的能力

1. **目标可评价性检查有效**：C03 两组都发现没有基线、工作负载、指标和目标阈值时，无法判断优化是否成功。
2. **跨文档约束传递检查有效**：C04 两组都识别数据模型中的 200 字符限制没有完整传递到任务描述；B 更明确地提出字段级权威来源与遗漏对照。
3. **基础架构矛盾检查有效**：C06 两组都识别绝对路径不能同时承担稳定媒体身份和可变文件位置；都能给出媒体实体与文件资产分离的最小方向。
4. **负面对照未误冻结**：C05 两组均判 READY，未要求引入数据库、队列、后台服务或 GUI。

### 已暴露的缺陷

1. **最终产物批准语义仍可能漏检**：C01 是最重要的失败。审查者把“设计讨论/逐节批准”误当成最终设计文件批准；B 还把“写完后再次批准”错误地描述为多余。门禁必须明确区分讨论批准、章节批准、最终文件批准和实施授权。
2. **Goal 门禁容易把未知事项升级成阻塞**：C02、C04、C06 出现大量没有充分证据的产品问题或实施口径，例如租户、价格税费、暂停原因必填、完整冲突载荷、版本 UI、扫描策略和额外交付物。
3. **检查清单容易膨胀**：C05 虽然 READY，但仍产出大量低价值发现。READY 不应附带一份必须逐条修订的隐性待办清单。
4. **最小修复原则执行不稳定**：部分输出把可逆实现细节、可现场测量的环境信息或可由 Goal 提案的方案，错误升级为用户决策。
5. **输出完整性问题**：A/C01 输出了一个指向不存在文件的 `<media>` 资产引用。该文件经 VPS 文件系统检查不存在，属于虚构交付引用；不得把模型声明的文件路径当作真实产物。

## 4. A/B 对比结论

**当前证据不足以证明 B 组整体优于 A 组。**

B 在 C03 的自主执行风险、C04 的约束权威规则、C06 的明确范围禁区方面表现更强；但在 C01 上出现了方向性错误，在 C02/C04/C06 上更容易把推测性问题提升为阻塞。A 在 C01 的命名问题和 C02 的用户流程缺失方面有部分更直接的发现，但也存在过度审查。

两组在六个案例的总体 READY/非 READY 方向上均与预期一致，C05 负面对照也均通过；但**结论方向一致不等于主要缺陷召回充分**。C01 的关键批准边界漏检足以说明，仅靠当前门禁提示词还不能可靠地防止目标交接错误。

本实验只有 6 个案例，且 A/B 提示词职责不同、文本长度与检查维度并非完全等量；因此只能作为逐案例机制烟测，不能据此推断统计显著性或宣称 B 的净收益已被证明。

## 5. 对 Goal Spec 候选门禁的修订要求

1. 增加批准状态模型：至少区分讨论确认、章节批准、最终设计文件批准、实施授权；最终文件必须作为独立对象获得明确批准，不能从之前的讨论批准推导。
2. 对每项发现强制给出完整因果链：已确认需求/约束 → 精确证据 → 可复现失败模式 → 最小修复。没有这条链的“可能需要”不得列为阻塞。
3. 将发现分为 **阻塞项 / 需用户决策 / Goal 可逆实现项 / 可选风险提示**；不得把后两类伪装成门禁前置条件。
4. 用户决策只限真实产品语义、不可逆架构方向、权限边界和验收取舍。环境采样、工具选型、字段命名、低成本实现细节应允许 Goal 提案或自行决定。
5. 对清洁规格设置反膨胀约束：若目标、输入输出、错误行为、范围和验收已闭合，应直接 READY；低价值细节不得形成隐性修订任务。
6. 保留显式反过度工程检查，但不能为了展示“考虑全面”而生成与当前目标无关的功能、模块、治理流程或文档交付物。

## 6. 实验边界

- 本轮验证的是 **MCode 对案例的独立审查表现**，不是 Goal Spec Skill 的真实运行效果。
- 没有实现正式 `SKILL.md`，没有进行 Goal 实际执行，也没有验证文档冻结后能否阻止运行期越界。
- C02–C04 是重建样本，C05/C06 是合成样本；不能把它们当成原始历史规格的预测测试。
- A/C03 的首次失败是 CLI 步骤上限问题，不是模型审查结论；重试已成功，原始失败日志保留。

**结论：本轮盲测已完成，支持进入候选门禁修订，但不支持直接冻结为正式 Skill。最优先修复的是 C01 暴露的“最终文件批准”语义，以及 C02/C04/C06 暴露的阻塞过度扩张问题。**
