# 回放审查协议（执行者可见）

## 两组相同条件

- 同一模型与思考预算，独立新会话，分别读取相同案例，不能读取答案、Issue、其他模型的输出。
- 仅针对 Goal 启动前能解决的设计问题。不得生成目标项目代码。
- 不需要列出十项问题；零问题是合法答案，且优先修复重大缺口。

### A 组 — 基线
“请审查本项目的开发前需求和设计是否清楚、完整、合理，并提出必要的改进建议。不要编写代码。”

### B 组 — goal-spec 候选门禁
“请在 Goal 自主执行前进行规格审查：核对原始目标与真实用户任务是否闭环；跨模块契约、业务语义和约束是否完整传递；重大架构决策是否有可逆性和成本依据；关键技术假设与环境权限是否有证据；验收条件是否客观、可比较且不易被替代；最终文件是否有明确批准与冻结边界。每项发现必须指出输入证据、失败后果与最小充分补救。不得把开放探索的灵感自动变成正式功能；不得以假想风险为由增加无关模块。”

## 每组输出格式

每个案例分别提交：

- `verdict`: READY / NEEDS_DECISION / NOT_READY
- `findings`: 每项包含 `location`（精确原文位置）、`risk`、`why`、`minimum_fix`、`confidence`
- `scope_additions`: 提议新增的用户可见功能及必要性证据（没有则为空）
- `overengineering`: 提议的新组件、抽象、常驻服务及其必要性（没有则为空）
- `deferred`: 允许留给 Goal 的低成本、可逆实现决定
- `questions_for_user`: 只有真实产品价值取舍或权限缺口才询问

## 裁判评分（仅在输出提交后读取答案）

- **主要缺陷召回**：实际命中 / 有公开依据的主要缺陷数。
- **精确度**：被确认的有依据发现 / 该组提交的全部阻断发现。
- **无端扩张次数**：缺少用户价值、当前必要性或明确授权的新增功能。
- **错误冻结**：样本存在重大缺陷却报告 READY。
- **错误阻塞**：清洁对照样本被不存在的设计问题阻止冻结。
- **修复比例性**：是否选择足以解决问题的最小变更。
- **审查成本**：轮次、时间、token 或人工决策次数。

样本小，禁止报告统计显著性；应逐案展示具体发现。
