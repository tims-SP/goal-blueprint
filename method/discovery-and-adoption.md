# 需求发现与采纳协议（候选方法 v0.1）

## 目的与边界

本协议规定：如何从不完整的产品构想中主动发现候选需求，并将其转化为经过明确决策的需求基线。

它是 Goal 启动前规格设计方法的一部分，不是正式 Skill，也不负责生成产品代码、替用户作业务决策或替代后续架构设计。

核心原则：

1. 用户没有提到某项能力，不代表该能力没有必要。
2. 模型发现某项能力，不代表用户已经需要或授权实现它。
3. 领域惯例、竞品功能和技术便利性只能提供发现线索，不能自动成为需求。
4. 只把已确认目标、已采纳需求及其必要约束写入正式需求基线。
5. 未决事项必须显式保留，不得由 Goal 自行补成产品决策。

## 输入与输出

### 输入

- 用户当前提出的产品想法、目标和已知约束。
- 用户明确提供的资料、现有系统信息和相关证据。
- 为回答具体问题而进行的领域研究、用户任务分析和技术可行性调查。

不得假定未提供的用户偏好、业务规则、用户群体或外部系统已经确定。

### 输出 A：探索记录（Discovery Log）

记录候选发现、证据、推断、影响、待确认事项和决策状态。探索记录可以包含被拒绝、暂缓和未验证的候选项；它不是 Goal 的实施授权。

### 输出 B：需求基线（Requirements Baseline）

只包含已确认的产品目标、已采纳需求、适用边界和可追溯的必要约束。它是后续规格设计的输入，不应混入待决策候选项。

两份输出通过稳定的发现 ID / 需求 ID 关联。探索记录中的状态变化不得静默改变需求基线。

## 探索流程

探索不是按清单机械填表。根据产品类型和已知风险选择相关路径；每条路径都必须说明它能帮助回答什么问题。

### 1. 用户目标与端到端任务

从用户想完成的结果出发，而不是从功能名称出发：

- 用户是谁、在什么情境下遇到问题？哪些角色已确认，哪些只是推测？
- 用户从触发任务到完成目标经历哪些步骤？
- 当前如何完成任务？有哪些人工操作、替代工具或失败点？
- 产品负责完整任务的哪一段？与外部角色或系统如何交接？
- 怎样观察到用户目标确实完成？

### 2. 领域与业务流程

按实际领域选择探索深度：

- 关键参与者、核心实体、业务事件和状态是什么？
- 主要流程、分支、异常和恢复路径是什么？
- 哪些规则影响数据含义、状态转换、权限或结果正确性？
- 是否存在多个看似相同、实际语义不同的用户任务？

领域模型和行业惯例用于提出问题与候选项，不得直接替用户确定产品策略。

### 3. 外部生态与约束

仅在可能影响目标或设计决策时研究：

- 必须交互的系统、平台、协议、格式或服务是什么？
- 有哪些已适用的法规、标准、平台政策或兼容性要求？
- 竞品或行业实践揭示了哪些用户任务或失败模式？
- 哪些差异是本产品必须支持的，哪些只是可选竞争能力？

研究结论必须区分一手资料、可靠二手资料、行业惯例和模型推断。不能把竞品功能清单复制为需求清单。

### 4. 失败场景与演进约束

围绕已确认目标识别实质性风险：

- 哪些失败会使核心任务无法完成、结果错误或数据不可恢复？
- 数据身份、迁移、冲突、权限、安全、隐私和恢复是否影响当前目标？
- 哪些决策一旦实施难以更改？其代价和证据是什么？
- 哪些未来能力只需要保持可演进性，当前不应实现？

只有影响当前目标、必要约束或高代价不可逆决策的演进问题，才进入当前规格决策。

## 候选发现的记录格式

每项候选发现使用稳定 ID，并至少记录：

| 字段 | 要求 |
|---|---|
| 标题 | 描述具体问题或能力，不使用泛泛口号 |
| 类型 | 用户任务 / 领域规则 / 质量属性 / 外部约束 / 失败场景 / 演进风险 |
| 证据 | 用户原话、观察资料、来源链接或明确标记的推断 |
| 证据等级 | E1 用户明确确认；E2 当前系统或可靠资料直接证实；E3 领域惯例/可靠二手证据；E4 合理推断；E5 未验证假设 |
| 用户价值 | 它改善哪个已知目标或避免什么实际损失 |
| 不处理的后果 | 具体影响；若未知则明确写未知 |
| 成本与复杂度 | 实现、运行、维护和认知负担的初步估计，注明不确定性 |
| 风险与替代方案 | 可能引入的问题，以及更小的处理方式 |
| 决策状态 | 见下文状态定义 |
| 关联关系 | 支持它的目标、依赖需求、冲突项或来源 |

不得仅凭 E4/E5 推断将候选项写成已确认需求。证据等级不是机械评分；高影响但低置信度的事项应优先验证或询问，而不是直接采纳。

## 决策状态与权限

每项候选发现必须处于以下一种状态：

- **Accepted**：用户明确采纳，允许进入需求基线。
- **Rejected**：用户明确拒绝，记录理由，禁止进入当前需求基线。
- **Deferred**：有潜在价值，但当前不纳入范围；记录重新评估触发条件。
- **Needs Decision**：存在真实的产品价值、成本、风险或不可逆取舍，必须由用户决定。
- **Unverified**：关键事实尚无足够证据；先研究或验证，不得伪装成需求。
- **Derived Constraint**：由已采纳需求必然推导出的实现约束。必须记录父需求、推导逻辑和影响；不得借此新增用户可见功能。

权限规则：

1. Agent 可以自主研究、提出候选项、比较方案和指出矛盾。
2. Agent 不得把候选项、行业惯例或推断自行升级为 Accepted。
3. 用户明确采纳是新增产品需求的授权；用户已明确提出的目标和约束也应作为基线来源记录。
4. 技术上必需的 Derived Constraint 可以由设计推导，但必须可追溯、可质疑；若它改变用户可见行为、成本、风险或产品承诺，则转为 Needs Decision。
5. Goal 只能执行需求基线中已采纳的范围。遇到会改变目标、用户可见行为、不可逆架构方向或授权边界的未决事项，必须停下请求决策。
6. 低成本、可逆且不改变外部行为的实现细节，可以留给后续设计或 Goal 提案，不要求用户逐项批准。

## 何时必须询问用户

只在答案会改变以下事项时询问：

- 用户目标、目标用户或端到端任务边界；
- 用户可见功能、业务语义或数据承诺；
- 明显影响成本、隐私、安全、权限或运营负担的取舍；
- 高代价或难以逆转的架构决策；
- 验收标准、质量目标或成功条件；
- 是否采纳某个有实质范围影响的候选需求。

提问应提供：需要决定的事项、可行选项、各自影响、当前证据和推荐方案。不要把多个互不相关的决定捆成一个问题。能通过可靠研究解决的事实问题，不要转嫁给用户。

## 需求基线生成规则

每条进入需求基线的需求必须：

1. 有明确来源：用户原始目标、用户明确采纳，或可追溯的 Derived Constraint。
2. 描述可观察的结果或行为，而不是仅描述实现方案。
3. 标明适用角色、触发条件、输入/输出、主要结果和必要的失败行为（适用时）。
4. 标明范围内与明确不做的内容。
5. 能关联到后续设计和验收，不允许孤立需求。
6. 不与其他已采纳需求、约束或业务规则冲突；发现冲突时先解决或标记 Needs Decision。
7. 不把尚未验证的推断写成事实。

需求基线应保留需求 ID、来源发现 ID、状态、理由和变更记录。后续规格中的业务规则、数据约束、模块契约和验收条件必须能追溯回需求基线；反向也必须能发现没有被设计或验收覆盖的需求。

## 探索停止条件

当以下条件同时满足时，结束当前轮探索并进入规格设计：

- 已理解核心用户目标和主要端到端任务，重要角色与边界有证据或明确标记未知；
- 对当前目标有实质影响的领域规则、外部约束和关键失败场景已经识别；
- 影响产品范围、用户可见行为、不可逆决策和验收的候选项已采纳、拒绝、暂缓或明确等待用户决定；
- 剩余未知项不会阻止下一阶段，或已明确列为阻塞决策；
- 继续研究的预期结果不会改变当前需求采纳、关键设计方向或验收标准。

不要求穷尽整个行业，不要求把所有低概率风险写入规格，也不以发现数量衡量探索质量。若新证据可能改变已采纳需求，应重新打开相关决策并记录变更。

## 质量检查

在发布需求基线前检查：

- **遗漏风险**：是否只复述用户原话，而没有研究完整任务和关键领域流程？
- **证据质量**：是否把惯例、竞品功能或推断冒充用户确认？
- **范围膨胀**：每项采纳需求是否都能说明用户价值和当前必要性？
- **决策权限**：是否有未经用户采纳的产品功能或承诺？
- **可追溯性**：每项需求是否有来源，每项重要发现是否有最终状态？
- **完整性**：核心任务是否存在未解释的关键步骤、业务规则或失败路径？
- **停止纪律**：是否继续研究了不会改变决策的低价值问题？

检查失败时只修复有证据的缺口，不通过增加无关模块、文档或审批流程来制造“完整感”。

## 本协议的验证方式

本协议在被视为有效方法前，至少需要一次端到端试运行：

1. 选择一个真实但尚未完整规格化的产品想法。
2. 在不预先提供完整功能清单的条件下，按四条探索路径工作。
3. 保存探索记录，明确区分事实、推断和未知。
4. 对有实质范围影响的发现向用户提出决策；不得代替用户采纳。
5. 生成需求基线，核对每条需求的来源和状态。
6. 由独立审查者检查遗漏、无依据扩张、决策越权和追溯断链。
7. 记录用户修正和遗漏，修订协议后再判断是否足以形成后续规格设计方法。

一次试运行只能证明协议在该案例中的可用性，不能证明对所有产品领域普遍有效。
